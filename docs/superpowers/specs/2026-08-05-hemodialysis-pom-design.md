# 血液透析模块 POM 设计

## 目标

为主任角色可见的“血液透析”模块建立可分批扩展的 Playwright POM。每个页面对象明确标识所属模块，并使用中文注释说明定位器和公开操作。

## 范围

- 覆盖主任角色在“血液透析”一级菜单下可见且可访问的页面。
- 首批按以下顺序实施：透析单/患者入口、透析处方、透前评估、临时医嘱；随后按实际菜单继续扩展。
- 每一批覆盖页面加载、菜单入口、筛选和表格、表单字段，以及页面已有的主要操作。
- 不封装 CRRT、今日医嘱、透析准备、透析监测、交班日志等其他一级菜单的页面。

## 目录与职责

新增 `pages/hemodialysis/` 包，全部页面对象放在该目录：

- `hemodialysis_page.py`：血液透析模块入口，负责验证模块已加载、点击模块内菜单，并提供通用页面状态读取。
- `dialysis_sheet_page.py`：透析单和患者列表入口。
- `prescription_page.py`：透析处方页面。
- `pre_dialysis_assessment_page.py`：透前评估页面。
- `temporary_orders_page.py`：临时医嘱页面。

所有类继承现有 `BasePage`。类中定义 `MODULE_NAME = "血液透析"`，作为模块归属标识；类、定位器分组和公开方法均使用中文文档字符串或必要的中文行内注释。

## 页面对象接口

每个业务页面对象提供以下稳定接口：

- `open()`：从模块入口进入对应页面，或在页面已有直达地址时导航并等待页面稳定。
- `is_loaded()`：通过页面标题、核心标题或关键区域确认页面加载完成。
- 以业务动作命名的方法，例如 `search_patient()`、`open_prescription()`、`fill_assessment()`、`add_temporary_order()`；不将业务操作散落到测试用例中。
- 只暴露测试需要的读取方法，例如 `get_record_count()`、`get_current_patient_name()`；测试不直接访问私有定位器。

定位器优先级为可访问名称、稳定的 `id` 或 `name`、页面已有的业务属性；不依赖列表序号、动态生成的 CSS 类名或不稳定文本拼接。

## 分批数据流

测试从已有登录态进入透析单页面。`HemodialysisPage` 验证当前处于血液透析模块，业务页面对象再通过菜单或患者入口进入目标页面。测试只调用 POM 的公开方法并断言可观察结果，例如页面已加载、查询结果出现或表单状态更新。

每次新增页面前，先在可视化登录会话中读取快照和元素属性，再确定实际定位器；页面未加载、菜单不存在或角色无权限时，POM 使用明确的等待与断言给出失败信息，不使用固定等待时间掩盖问题。

## 测试策略

- 每个新增 POM 的公开加载检查和一个主要业务动作，先在 `tests/` 中编写失败测试。
- 先运行新增测试，确认因对应 POM 尚不存在或行为尚未实现而失败。
- 再实现最小 POM 方法，使测试通过。
- 页面访问依赖真实登录态时，测试复用 `auth/storage_state.json`；登录流程测试继续保留 `no_auth_state` 标记。
- 每批完成后运行该批测试和完整 `pytest` 回归。真实站点不可达时，明确记录网络失败原因，不将其误报为 POM 缺陷。

## 风险与边界

系统页面可能按机构、患者状态或角色改变可见字段。POM 只封装主任角色当前可见的页面与元素；遇到动态字段时，通过页面标签、字段名或可见区域定位，不假设所有患者都具有完全相同的表单。
